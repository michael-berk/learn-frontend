fde-one apx migration syllabus

60 hours over 6 weeks. Calibrated for a senior backend/AI engineer: it skips what you already own (API design, SQL/pg, auth, concurrency, deploy, testing discipline) and concentrates on what's genuinely new — the React rendering model, CSS and layout, design systems, and shipping polished production frontends. Games are the forcing function; the matching fde-one refactor runs alongside.

The north star — hold this and everything else follows. The one thing that separates great React engineers from competent ones isn't a library; it's a mental model: render is a pure function of state, and useEffect exists only to synchronize with systems outside React. The two habits that fall out of it are what every game drills — derive, don't store (compute values during render instead of mirroring them into state via an effect) and colocate, don't lift (keep state in the lowest component that needs it; reach for Context or a store only on real sharing). As a backend engineer your instinct will be to reach for an effect to "do work" — that instinct is the single most common senior-backend-to-React bug. If a game's rule here ever feels arbitrary, trace it back to this.
Backend stack: Hono first, then AppKit. Weeks 3–5 build the game backends on Hono — a thin router that leaves the request lifecycle, middleware, and typed client visible, so you learn the primitives bare. Week 6 migrates a game to AppKit (@databricks/appkit), Databricks' first-party SDK, so you can see exactly what a framework abstracts once you've done it by hand. fde-one's real end state is AppKit — officially supported, not a bespoke stack. The Hono work on fde-one in weeks 3–5 is a deliberate learning rehearsal of the API shape before the AppKit cutover.
TypeScript depth is woven in, not drilled. You know types from Python, so there are no type-theory exercises — but "really good at TS" means the half you don't have yet: making illegal states impossible to compile. Each game carries one applied TS challenge (a ▸ TS line in its must-use) building toward that — discriminated unions for game state, generics for reusable components, inference for the typed client. It pays off directly in your AI work: the same techniques type LLM tool-call schemas, agent state machines, and structured outputs.
Reading this as a backend engineer. The backend weeks (3–5) are deliberately thin — Hono/pg/auth/deploy are your existing skills in new syntax, so those sections just name the syntax and move on, with no test. The weight is in weeks 1, 2, and 6: the browser runtime, reconciliation, CSS/layout, and production polish. That's where strong backend engineers actually get stuck.

Removing apx retires five couplings: the dev loop, the generated OpenAPI client (lib/api.ts), _metadata.py, the shadcn registries, and the apx MCP tools. Config is only [tool.apx.*] in pyproject.toml; the rest is behavior, none of it conceptually hard for you. fde-one's target is AppKit, which supplies its own dev loop, typed client, and build — so adopting AppKit retires most of those couplings at once rather than hand-rebuilding each.

Weeks

Week 1Tic-Tac-Toe

The React mental model and the styling system. The whole point is unlearning imperative/stateful habits.

Tangible outcome

A styled, playable tic-tac-toe — the first page of your capstone repo — built the idiomatic React way, not as a DOM-mutation script.

Learning outcomes

render-as-function-of-stateone-way data flowderived vs stored state immutabilityJSXcomposition / childrencompound components controlled vs uncontrolledTailwindshadcn + cn()
Assumed known, not taught: components as functions, props as arguments, event handling, data structures. The new ideas: you describe UI as a pure function of state and never touch the DOM yourself; you compose UI by passing children and slots rather than configuring via flags; and who owns a value's state — React or the DOM (controlled vs. uncontrolled) is a deliberate choice, not a default.

Game — success criteria

  • The entire board is a function of one state value — you never imperatively update a cell.
  • Whose-turn and the winner are never stored; they fall out of the state.
  • Resetting is a state change, not DOM surgery.
  • It looks intentional, using the real component system rather than raw HTML.

Must use to learn: a single useState for the board; the winner/turn computed on each render; a new array on every move (no mutation); shadcn Button/Dialog styled through cn()/tailwind-merge. Build a reusable <Cell> that takes children, and use the Dialog as the compound component it is (DialogTrigger/DialogContent) rather than a boolean-driven modal.

▸ TS challenge: model the game result as a discriminated union ({status:'playing'} | {status:'won', winner:'X'|'O'} | {status:'draw'}) so the UI can't read winner in a state where it doesn't exist. Use as const on the cell values so 'X'|'O'|null is inferred, not widened to string.

FDE One — refactor

  • No code change. Map the apx surface (grep apx, _metadata.py, lib/api.ts) and open the "apx removal" issue with the five couplings. This is reconnaissance you can do fast.

Test — frontend judgment (new material only)

  1. You mutate the board array in place and call setState with it. The UI doesn't update. Why — and what's the model being violated?
  2. Why is "whose turn" derived state and not its own useState? What class of bug does storing it invite?
  3. In React you never write to the DOM directly. What is the framework actually doing on your behalf, and why does that constraint exist?
  4. When would cn() / tailwind-merge change the output versus a plain template string of classes?
  5. You want a win modal. Why reach for a shadcn Dialog (focus trap, portal, escape) instead of a conditionally-rendered styled div?
  6. A compound component (<Dialog><DialogTrigger/><DialogContent/></Dialog>) vs. one that takes a dozen boolean/render props — what does the composition style buy the caller?
  7. Give one value in this game you'd keep uncontrolled (DOM-owned) and one you'd control in React. What's the deciding question?

Week 2Connect Four

Reconciliation, why re-renders happen, refs, and accessibility. The genuinely non-obvious React.

Tangible outcome

A routed, keyboard-playable Connect Four whose rendering you can explain and profile — you know what re-renders on each move and why.

Learning outcomes

reconciliation + keysre-render causesuseMemo / useCallback useRef vs stateeffect timing + cleanupexhaustive-deps effects you don't needContext + providerContext re-render pitfall DOM events / bubblingportalsTanStack Router ARIA / focus mgmtReact DevTools Profiler
Assumed known: routing as a concept, state management in the abstract, event loops. New: React's diffing algorithm, the exact triggers for a re-render, when memoization helps vs. hurts, refs as the escape hatch, Context for tree-wide state (and why it re-renders every consumer), the deps array as a discipline you don't lie to, when an effect is the wrong tool, and the browser primitives React sits on (event bubbling, portals).

Game — success criteria

  • You can state, for a single move, which components re-render and justify each.
  • Nothing re-renders that didn't need to — proven in the Profiler, not assumed.
  • An imperative concern (animation, focus, measuring a node) is handled without forcing a re-render.
  • Shared state (theme or current player) reaches deep components without prop-drilling, and you know what it costs in re-renders.
  • Fully operable and announced by keyboard and screen reader; routed via URL.

Must use to learn: a deliberate useMemo/useCallback you can prove earns its place; a useRef for an imperative task (focus or measure); an effect with cleanup for the drop animation; a Context provider for theme or current-player (observe which consumers re-render); at least one place you deliberately avoid an effect by deriving state or using an event handler; TanStack Router for menu → game; ARIA roles + keyboard handlers on the grid, with the win popup rendered through a portal.

▸ TS challenge: write a generic <Grid<T>> (or useGrid<T>) that works for any cell type, so Connect Four and tic-tac-toe share it with no any. The compiler should infer the cell type from the data you pass in.

▸ Modern-React note: React 19's Compiler auto-memoizes, which is making hand-written useMemo/useCallback largely unnecessary in new code. Do them by hand here to learn why they exist and when they help — then note that the Compiler is the direction of travel, so you reach for them deliberately, not reflexively.

FDE One — refactor

  • No code change. Trace one route end to end and document the useXSuspense / selector() pattern and how the router tree is generated — you'll reproduce both later.

Test — frontend judgment (new material only)

  1. A parent re-renders. Which children re-render by default, and what actually stops the cascade?
  2. You wrap a value in useMemo and see no change. Give two reasons memoization can be useless or net-negative here.
  3. When does a list need stable keys beyond "React complains," and what's the visible bug with index keys in a reorderable list?
  4. You need to focus the active column on each turn. Why is that a useRef + effect job and not state?
  5. An effect reads the board but only lists [] as deps. What's the stale-closure failure mode in gameplay terms?
  6. You put game logic in a useEffect that watches a move and sets more state. When is that a code smell, and what replaces it?
  7. You move theme into Context and now a deep component re-renders on every unrelated theme-adjacent change. Why, and how do you contain it?
  8. When is Context the right tool versus lifting state, prop-drilling, or server state? What's the test?
  9. A click on a child also fires a handler on an ancestor. Explain the mechanism and how you'd stop it — and why React's event system matters here.
  10. Why does a modal/popover often need a portal, and what breaks (stacking, overflow, focus) if you render it inline?
  11. In the Profiler you see the whole board re-rendering per move. What's your decision tree before reaching for memoization?
  12. What has to be true for a grid of divs to be fully keyboard-operable and screen-reader-correct?

Week 3Wordle

A backend you already know how to build, in Hono syntax — plus the frontend data-fetching lifecycle, which is new.

Tangible outcome

Wordle with a Hono + Lakebase backend. You wrote the server in an hour; the learning is in how the client consumes it.

Learning outcomes

Hono (syntax)fetch in Reactloading/error/success states TanStack Query basicsrequest lifecycle in UI
Assumed known — stated, not taught: routing, middleware, Zod validation, pg, auth headers, "scoring belongs server-side," concurrency. You've done all of this. Hono is just the syntax; skim its docs and port your instincts. New: representing an async request's states in a UI without race conditions.

Game — success criteria

  • The server owns the word and scoring (obvious to you — just build it).
  • The UI distinctly represents loading, error, and success for every call — no flashes of wrong state, no stuck spinners.
  • A slow then fast request can't render out of order.
  • The word list is data, static-site-ready for week 6.

Must use to learn (frontend side): TanStack Query for the guess call, surfacing its loading/error/data states in the UI. The Hono API itself is a translation exercise, not a lesson.

▸ TS challenge: define the guess-response type once on the server and have the client infer it (Hono's typed client / z.infer from the Zod schema) — no hand-written client type, no drift. This is the exact pattern you'll use to type an LLM's structured output or a tool-call result.

FDE One — refactor

  • Reimplement fde-one's simplest read-only router in Hono (router → service → dao); diff JSON against FastAPI for parity. This is a rehearsal — the real cutover (week 6+) targets AppKit, but doing it in bare Hono first teaches you the API shape so AppKit's abstractions make sense.

Test — frontend judgment (new material only)

  1. Hand-rolling fetch + useState, name three UI states you must handle and the race condition you'll hit if you don't.
  2. What does TanStack Query handle for you that you'd otherwise write by hand, and when is it overkill?
  3. Two guesses fire quickly; responses return out of order. How does the UI avoid showing the wrong one?

Week 4Wordle Leaderboard

Server-state caching, forms, and the async UI states that have no backend analog.

Tangible outcome

A leaderboard that updates without a refresh and a settings form that validates inline. Client/server share types with no generated client.

Learning outcomes

cache keys + invalidationoptimistic updatesuseMutation custom hooksreact-hook-formcontrolled vs uncontrolled composed Suspense + error boundariesHono RPC types
Assumed known: schema validation (you'll use Zod but you know validation), what a type contract buys you, HTTP semantics, when to persist. New: client-side cache as a first-class concern, optimistic UI + rollback, React's form ergonomics (controlled inputs, uncontrolled refs, re-render cost), extracting stateful logic into a reusable custom hook, and composing Suspense + error boundaries so each slice of the tree has its own loading and failure handling.

Game — success criteria

  • Finishing a game reflects on the leaderboard immediately, then reconciles with the server.
  • If the write fails, the UI rolls back cleanly — no lie left on screen.
  • The settings form validates inline without re-rendering the world on every keystroke.
  • The leaderboard's data logic lives in a reusable hook, not inline in the component.
  • A render-time error in one widget doesn't blank the page; the rest keeps working.

Must use to learn: useQuery + useMutation with explicit cache keys and invalidation; one optimistic update with rollback; a custom hook (e.g. useLeaderboard()) that encapsulates the query + mutation and returns a clean API; a react-hook-form form (notice the uncontrolled design and why); a Suspense boundary and an error boundary scoped to one panel so its loading/failure is isolated; a shared Hono RPC type.

▸ Modern-React note: React 19 added Actions and the hooks that formalize exactly what you're hand-building this week — useOptimistic (optimistic state + rollback), useActionState and <form action> (pending/error plumbing), and use() (read a promise or context in render). Build the leaderboard once the manual way to understand the lifecycle, then re-implement the optimistic update with useOptimistic and compare. Knowing both is the point — fde-one and AppKit may use either.

▸ TS challenge: type the custom hook's return as a discriminated union on status (loading | error | ready) so a caller can't read data before it exists — the compiler forces the loading/error branches.

FDE One — refactor

  • Point one real fde-one screen at its Hono endpoint through the typed client; delete that slice's dependency on apx-generated api.ts + axios, keeping useXSuspense ergonomics.

Test — frontend judgment (new material only)

  1. Client-side cache invalidation is "one of the two hard problems" here too. After a mutation, what are your refresh strategies and when does each win?
  2. Walk the optimistic-update lifecycle: what you show immediately, what you keep to roll back, and what happens on failure.
  3. Why can an uncontrolled (react-hook-form) input outperform a controlled one, and when would you still want controlled?
  4. You extract useLeaderboard(). What belongs inside the hook vs. the component, and what makes its return API good?
  5. Two components call useLeaderboard(). Do they share state/fetch or each get their own? What decides that, and when is it a bug?
  6. Where do you place Suspense and error boundaries so one failing panel doesn't take the page, and what should the error boundary deliberately not catch?
  7. A query key collides between two screens. What's the symptom, and how do you design keys to prevent it?

Week 5Stats dashboard + deploy

CSS layout and charts (new) plus build/deploy (your turf, in new syntax).

Tangible outcome

A multi-panel stats dashboard that is actually laid out well — and deployed as a live Databricks App. The deploy is routine for you; the layout is the lesson.

Learning outcomes

flexboxCSS gridresponsive layout spacing + alignmentrechartssonnerVite build (syntax)
Assumed known: build pipelines, serving a SPA from a backend, the Databricks Apps runtime contract, port/foreground rules, env config. You own deployment. New: CSS as a layout engine — flex vs. grid, intrinsic sizing, responsive behavior, and making a dense dashboard read cleanly without a designer.

Must use to learn: a CSS grid for the panel layout; flexbox within panels; a responsive breakpoint that reflows rather than scrolls; a recharts chart sized by its container; a sonner toast. Build/deploy via your own entrypoint.sh + app.yml — translate your existing knowledge.

FDE One — refactor

Note which of these AppKit provides out of the box, so week 6 you know what to delete.

Test — frontend judgment (new material only)

  1. Flexbox vs. grid for a dashboard: what question decides which you reach for?
  2. A panel's content overflows its box on narrow screens. What are the usual CSS causes and the idiomatic fixes?
  3. Why size a chart to its container rather than fixed pixels, and how do you make that happen?
  4. You want three columns on desktop and one on mobile with no JS. How, and what makes it reflow rather than shrink?
  5. Two sibling panels won't align their baselines. What's typically wrong and how do you debug it?

Week 6Hono → AppKit

Migrate a game off bare Hono onto AppKit, and see exactly what a framework abstracts once you've built it by hand. Sets up fde-one's real cutover.

Tangible outcome

One game (Wordle or the leaderboard) rebuilt on AppKit — same behavior, far less plumbing — plus a written diff of what AppKit replaced. You can now justify fde-one's AppKit target with evidence, not faith.

Learning outcomes

AppKit SDKplugin modelAppKit typed data framework vs. library trade-offmigration diffingappkit-ui
Assumed known: everything the Hono weeks taught you to do by hand — routing, middleware, the typed client, build/deploy. New here is purely comparative: which of those AppKit owns, what it costs you in control, and when a framework is worth it. You're evaluating a tool, which is squarely a staff-engineer skill — the test reflects that.

Game — success criteria

  • A game that worked on Hono works identically on AppKit, with the hand-rolled plumbing gone.
  • Data access goes through AppKit's typed layer / Lakebase plugin instead of your own pg wiring.
  • You can point at each thing you deleted and name the Hono code AppKit replaced.
  • You have a clear-eyed take on where AppKit helped and where it got in the way.

Must use to learn: AppKit's routing + data plugin (Lakebase) in place of your Hono routes and pg calls; at least one appkit-ui component; a short written comparison (what was deleted, what you lost control over). The migration itself is the lesson — don't add new game features.

FDE One — refactor (kicks off the real cutover)

  • Decide the fde-one AppKit cutover plan using what you just learned: which apx couplings AppKit replaces directly (dev loop, typed client, build) versus what still needs hand-work.
  • Migrate one fde-one route onto AppKit end to end as the proof of concept; open the "apx → AppKit" migration issue/PR.
  • Deferred to a week-7 follow-on (fund from slack): port the remaining routers, delete [tool.apx.*] + the apx MCP from .mcp.json, strip apx from docs, full staging parity pass, update CLAUDE.md until grep apx returns nothing.

Test — framework-evaluation judgment (new material only)

  1. Having built the Hono version, which specific pieces did AppKit let you delete, and which did it only rename?
  2. Where did AppKit cost you control, and is that trade acceptable for fde-one? Name the deciding factor.
  3. What does fde-one gain from AppKit that a well-maintained bare-Hono stack would not?
  4. Which apx couplings does adopting AppKit retire for free, and which still need hand-work?
  5. If AppKit's maturity disappointed on one axis, what's your fallback, and how would you de-risk the cutover?

Appendix — production-polish checklist (self-study)

Pulled out of week 6 so that week stays focused on the AppKit migration. Fold these into any game whenever you have spare hours; they're a checklist, not a lesson, for someone at your level.

  • Async states: every data-driven screen has a designed loading, empty, and error state — the empty state is the one most often skipped.
  • Bundle: run a bundle analysis before optimizing; code-split heavy routes (charts, maps); confirm the main chunk stays lean.
  • Accessibility: keyboard-operable, visible focus, semantic roles, color-contrast pass — the cheap, high-value checks before calling a frontend shippable.
  • Theming: light/dark via tokens so a toggle and the OS setting both work with no duplicated color logic.
  • Static site (optional): collect the games on GitHub Pages via Actions; backend games run client-only (bundled words, localStorage). A portfolio nice-to-have, not a learning goal.

TypeScript depth track (woven through the games)

The ▸ TS lines above are the applied version of this. The goal across the six weeks is to go from "typed Python" to making illegal states impossible to compile — the half of TS fluency that's genuinely new, and the one that pays off most in AI tooling (typing tool-call schemas, agent state, structured outputs). What each game drills:

  • W1 — discriminated unions + as const: game-result union; literal inference instead of widening.
  • W2 — generics + inference: a reusable <Grid<T>> that infers its cell type.
  • W3 — inference across a boundary: client infers the server's response type (z.infer / typed client), no hand-written types.
  • W4 — unions for async state: a hook whose return type forces the caller to handle loading/error before data.
  • React-specific surface, as you hit it: ReactNode vs ReactElement; event generics (MouseEvent<HTMLButtonElement>); forwardRef typing for Radix-composable inputs; satisfies to keep literal types without widening; the "context is undefined until provided" guard.
  • If you want pure reps: the type-challenges repo (GitHub) — do the easy + medium tiers; they cover infer, conditional/mapped types, template literals. ~8 hrs, optional, outside the games.

Modern React (React 19) — so you learn current, not 2023

The games teach the fundamentals by hand first (that's how you understand them), but know where React has moved so you reach for the modern primitive deliberately. Called out in W2 and W4; collected here:

  • React Compiler: build-time auto-memoization. Increasingly makes manual useMemo/useCallback unnecessary — learn them to understand the model, then lean on the compiler.
  • Actions + useActionState / useOptimistic / useFormStatus + <form action>: first-class pending/optimistic/error handling for mutations and forms. Replaces much of the manual plumbing you build in W4.
  • use(): read a promise (Suspense-aware) or context during render. Note the caveat: the promise must come from a Suspense-compatible cache, not one created in render.
  • Server Components / Server Actions: know conceptually what they are and the server/client boundary — but out of scope to build, since Databricks Apps serves a static SPA + API. This is the main place to ignore the generic "learn Next.js/RSC" advice.

Appendix — state libraries (know they exist, know why we skip them)

Redux / Zustand / Jotai / Recoil are the global-state libraries you'll see in other React codebases. fde-one — and this plan — deliberately use none: server state lives in TanStack Query (cache, refetch, invalidation), tree-wide UI state in Context, and local state in useState. That covers the vast majority of apps. Reach for a store library only when you have genuinely global, frequently-updated client state shared across unrelated trees — rare in a data-driven internal tool. Knowing the boundary is the skill; adopting one here would be the mistake.

Deliberately out of scope

Not taught, because you already have it: backend architecture, API/route design, SQL and pg, auth, concurrency, deployment mechanics, testing strategy, CI/CD, type systems, "where logic belongs." The Hono/Lakebase/deploy work appears only as syntax translation, never as a lesson. Also out: SSR / Next.js / RSC (Databricks Apps is a static SPA + API) and Redux / Zustand (fde-one uses TanStack Query + local useState).
