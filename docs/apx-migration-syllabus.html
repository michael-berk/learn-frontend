fde-one apx migration syllabus

60 hours over 6 weeks. Each week ships one playable game that teaches a skill fde-one uses, plus a matching refactor task in fde-one. The games assemble into a static GitHub Pages site. The Databricks data layer stays.

Syllabus at a glance

WkProjectCore skillYou will have built
1Tic-Tac-ToeReact + stylingA styled, interactive board
2Connect FourRouting + a11yA routed, keyboard-playable game
3WordleHono + Lakebase backendA game with a real API + DB
4Wordle LeaderboardTyped client + formsWrites, a leaderboard, a validated form
5Stats + deployCharts + build/deployA dashboard deployed to Databricks Apps
6Static siteTesting + GitHub PagesA live portfolio site of the games

Removing apx retires five couplings: the dev loop, the generated OpenAPI client (lib/api.ts), _metadata.py, the shadcn registries, and the apx MCP tools. Config is only [tool.apx.*] in pyproject.toml; the rest is behavior each week replaces.

Weeks

Week 1Tic-Tac-Toe

React fundamentals and fde-one's styling model. No backend.

Tangible outcome

A tic-tac-toe game you can play in the browser, styled with the same component system fde-one uses. It is the first page of your capstone repo.

Learning outcomes

componentspropsuseState event handlersderived stateconditional render list keysTailwind + shadcnTS props/events

Game — success criteria

  • Two players can take turns and the game knows whose turn it is.
  • The game detects a win or a draw and makes the result obvious.
  • A finished game can be started over without reloading the page.
  • It looks intentional, not like unstyled HTML.

Must use to learn: a Square child component driven by props; board state in a single useState; the winner computed from state, not stored separately; shadcn Button/Dialog styled with cn().

FDE One — refactor

  • No code change yet. Map the apx surface: grep apx, inventory _metadata.py and lib/api.ts, annotate tsconfig.json / biome.jsonc / vite.config.ts.
  • Open the "apx removal" tracking issue listing the five couplings.

Test — when/how would you use…

  1. You have one piece of data two components both need. Where does it live, and why not duplicate it?
  2. Whose-turn and the winner can both be computed from the board. Why store neither in its own useState?
  3. When is a value a prop versus state? Give a tic-tac-toe example of each.
  4. You render the 9 squares with .map(). Why does each need a key, and what makes a good one here?
  5. A click handler needs to know which square was clicked. How do you pass that without making 9 different functions by hand?
  6. What goes wrong if you mutate the board array directly instead of making a new one?
  7. When would you reach for cn() / tailwind-merge instead of a plain className string?
  8. You want a "You won" popup. Why a shadcn Dialog rather than conditionally rendering a styled div?

Week 2Connect Four

Routing, larger state, and accessibility. No backend.

Tangible outcome

A Connect Four game that lives behind its own route (a menu links to it), is fully playable with the keyboard, and handles a 42-cell board.

Learning outcomes

TanStack Routerroute params2D state lifting stateuseEffectcleanup keyboard eventsARIA / focusReact DevTools

Game — success criteria

  • From a landing screen, a player can navigate to the game and back by URL.
  • Dropping a piece respects gravity, and the game detects four in a row in any direction.
  • Everything playable with a mouse is also playable with only the keyboard.
  • A screen reader can tell whose turn it is and the state of a column.

Must use to learn: two routes via TanStack Router; the board as a single lifted state object; a useEffect that does something real (e.g. a drop animation or AI delay) with a cleanup; keyboard handlers and ARIA roles on the grid.

FDE One — refactor

  • No code change. Trace one real route end to end: component → useXSuspense hook → lib/api.ts → FastAPI route.
  • Write up the useXSuspense / selector() pattern and how the TanStack Router tree is generated — you reproduce both later.

Test — when/how would you use…

  1. When should two screens be two routes versus one component toggling state? What do you gain from routes?
  2. You need the game to know which board to load from the URL. How do route params get there, and when do they change?
  3. A column's win-check reads the whole board. Why keep the board in one state object rather than 7 column states?
  4. Name a thing in this game that belongs in useEffect and a thing that does not. What's the test?
  5. Your effect starts a timer. What breaks if you don't return a cleanup, and when does cleanup run?
  6. The board re-renders on every move. How do you confirm in DevTools whether that's a problem?
  7. How do you make a grid of divs operable and announced for keyboard and screen-reader users?
  8. When is a dependency array wrong, and how do stale closures show up in gameplay?

Week 3Wordle

Your first Hono + Lakebase backend.

Tangible outcome

A Wordle game where the word and guess-scoring live on a Hono server backed by a Lakebase word table, so the answer can't be read from the browser.

Learning outcomes

Hono routesmiddlewareZod validation pg / Lakebaseauth headersfetch TanStack Queryserver vs client state

Game — success criteria

  • The client never knows the answer until the game is over.
  • A guess that isn't a real word is rejected before it counts.
  • Each guess comes back scored (right spot / wrong spot / absent) and the UI reflects it.
  • The word list is data, not hardcoded in a component.

Must use to learn: a Hono API with GET + POST routes; Zod on the request body; a pg query against Lakebase; one piece of middleware (auth or logging); TanStack Query for the guess call. Keep a bundled word list too for week 6's static version.

FDE One — refactor

  • Reimplement fde-one's simplest read-only router in Hono, mirroring router → service → dao.
  • Run it beside the FastAPI version; diff the JSON responses until they match.

Test — when/how would you use…

  1. Why does scoring belong on the server here, not the client? What's the general rule for that decision?
  2. When do you validate with Zod on the server even though the client already checks the input?
  3. What belongs in middleware versus in a route handler? Give one of each from this game.
  4. The daily word is server state; the current typed guess is client state. How do you decide which is which?
  5. When do you reach for TanStack Query instead of fetch + useState?
  6. A pg query returns rows. Where do you shape them into the response the client wants, and why there?
  7. How do you pass Databricks auth to the DB without putting a secret in the frontend?
  8. Two users hit /api/guess at once. What about your handler must be safe, and what can be shared?

Week 4Wordle Leaderboard

A typed client contract and real forms.

Tangible outcome

Wordle now records results to Lakebase, shows a leaderboard, and has a settings form with validation. Client and server share types with no generated client.

Learning outcomes

useQueryuseMutationcache invalidation Hono RPC / shared typesreact-hook-formZod schema Suspenseerror boundarieslocalStorage

Game — success criteria

  • Finishing a game updates the leaderboard without a manual refresh.
  • The settings form refuses bad input and explains why, before it saves.
  • A failed network call shows a sensible fallback, not a blank screen.
  • Changing a type on the server surfaces as a type error in the client.

Must use to learn: useQuery for the leaderboard and useMutation for submitting a result, with cache invalidation; a shared type contract (Hono RPC); a react-hook-form form validated by a Zod schema; one error boundary.

FDE One — refactor

  • Point one real fde-one screen at its new Hono endpoint through the typed client.
  • Delete that slice's dependency on the apx-generated api.ts + axios, keeping the useXSuspense ergonomics.

Test — when/how would you use…

  1. After a mutation, the leaderboard is stale. What are your options to refresh it, and when do you pick each?
  2. What's a query key, and what happens if two queries accidentally share one?
  3. When does validation belong in the Zod schema versus in the submit handler?
  4. Why validate the same form data on both client and server?
  5. When is a controlled input worth the boilerplate, and when does react-hook-form avoid it?
  6. Where do you put an error boundary, and what should it catch versus let through?
  7. What does a shared type contract buy you over a hand-written client, concretely?
  8. You optimistically show a result before the server confirms. What must you handle if it fails?
  9. When is localStorage the right store, and when is it the wrong one?

Week 5Stats dashboard + deploy

fde-one's real UI surfaces and the build/deploy loop.

Tangible outcome

A stats dashboard for your games (charts, toasts, a markdown rules page) deployed as a live Databricks App you can send a link to.

Learning outcomes

rechartssonner toastsreact-markdown Vite builddev proxySPA from backend entrypoint.shapp.yml

Game — success criteria

  • The dashboard turns stored results into a chart that's readable at a glance.
  • Finishing a game gives immediate, non-blocking feedback.
  • In development, frontend and API run together with live reload.
  • In production, one process serves both, reachable at a URL you share.

Must use to learn: a recharts chart from real data; a sonner toast; a react-markdown page; a Vite dev proxy to the Hono API; a single-process production build launched by your own entrypoint.sh + app.yml on Databricks Apps.

FDE One — refactor

  • Write fde-one's entrypoint.sh + app.yml to build the UI and launch Hono.
  • Replace _metadata.py generation with a TS build-stamp step.
  • Reproduce apx dev check as tsc --noEmit + Biome in the Makefile.

Test — when/how would you use…

  1. When is a toast the right feedback, and when do you need something more blocking?
  2. Why does the dev server proxy /api instead of the frontend calling the backend's port directly?
  3. What's different about serving the built SPA from the backend versus running Vite in dev?
  4. What does entrypoint.sh have to guarantee for the Databricks Apps platform (port, foreground)?
  5. When do you compute chart data on the server versus in the component?
  6. What replaces apx's generated _metadata.py, and when does that value get stamped?
  7. Why run tsc --noEmit in CI when the app already builds?
  8. A deploy returns 502. What are the first two things you check given the entrypoint contract?

Week 6Static site + cut over

GitHub Pages and finishing the migration.

Tangible outcome

A live GitHub Pages site collecting the games (backend ones running client-only), with tests on the core logic — and fde-one running with zero apx.

Learning outcomes

VitestReact Testing Librarystatic build GitHub ActionsPages base pathclient-only data

Game — success criteria

  • Every game is reachable from one deployed URL with no server running.
  • The backend games still work using only what the browser has.
  • The game logic has tests that fail when the logic breaks.
  • A push to main redeploys the site on its own.

Must use to learn: a Vitest unit test on win-detection; one React Testing Library component test; a static Vite build with the correct Pages base; a GitHub Actions workflow that builds and publishes.

FDE One — refactor

  • Port the remaining routers to Hono; retire fde_one/backend (FastAPI).
  • Delete [tool.apx.*], remove the apx MCP from .mcp.json, strip apx from docs.
  • Parity pass on staging; open the migration PR; update CLAUDE.md. grep apx returns nothing.

Test — when/how would you use…

  1. What logic is worth a unit test here, and what isn't?
  2. When do you test through the rendered component (RTL) rather than the function directly?
  3. A backend game must run with no server. What has to change, and what can stay?
  4. Why does GitHub Pages need a base path, and what breaks if it's wrong?
  5. What should the Actions workflow do on a pull request versus on a merge to main?
  6. How do you prove fde-one has no remaining apx dependency, beyond the app booting?
  7. When would you keep the FastAPI backend behind a flag instead of deleting it?
  8. A test passes locally but fails in CI. What are the usual causes?

Not covered, by design

SSR / Next.js / RSC — Databricks Apps serves a static SPA plus an API, so these would mislead. Redux / Zustand — fde-one uses TanStack Query for server state and local useState, with no global store.

Open decision

Hono vs. AppKit (@databricks/appkit): Hono maximizes learning but is yours to maintain; AppKit is officially supported. Worth checking with #fde-one-dev before committing a shared repo.
